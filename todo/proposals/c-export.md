# Proposal: C export — Basic Next functions callable from C

## Status

**Draft (2026-10-07).** Scope agreed with Carlos in chat: functions only, shared
library only. Not scheduled in a bucket; nothing here is implemented. Open
decisions are marked `TODO (Carlos)`.

This is the reverse direction of [`bnffi.md`](bnffi.md) (BN calls C). It is a
**language change** and therefore cannot ride in bucket 0.6.6, whose claim is
"no language change".

## Example

```basic
EXPORT AS "C" FUNCTION Area(w AS FLOAT64, h AS FLOAT64) AS FLOAT64
    RETURN w * h
END FUNCTION
```

```sh
bnc --emit sharedlib -o libgeometry.dylib geometry.bn
```

```sh
bnc --emit c-header -o geometry.h geometry.bn
```

```c
/* geometry.h, generated by bnc */
double Area(double w, double h);
```

`Area` is still an ordinary `EXPORT` for Basic Next importers; `AS "C"` adds a
C symbol with the C calling convention of the target.

## Scope

**In:** module-level `FUNCTION` declarations marked `EXPORT AS "C"`, whose
signature uses only the types below; `bnc --emit sharedlib` (`.so`, `.dylib`,
`.dll`) with a generated C header.

**Out (decided 2026-10-07, Carlos):**

- `CLASS` — C has no classes. Not a future cut of this proposal.
- Static libraries, in both directions: `bnc` emits no `.a` / `.lib` archive,
  and `BNFfi` does not link static C libraries.

**Out of the first cut:** `STRUCT` by value, `STRING` results, vectors,
pointers, function types (callbacks), `T OR Error` / `OR NULL` signatures,
`ASYNC`, `DATE`, `TIME`, `TIMEZONE`, `TIMESTAMP`, `SYSTEM`, named types.

## Grammar

```ebnf
declaration = [ "EXPORT" [ "AS" abi-name ] ] ( function-declaration
            | class-declaration | struct-declaration | interface-declaration ) ;
abi-name    = string-literal ;   (* only "C" is valid *)
```

`EXPORT AS` is invalid today, so the production is unambiguous. A semantic
rule (not the grammar) restricts `AS "C"` to `function-declaration`.

**Decided 2026-10-07 (Carlos):** the ABI name is the string literal `"C"`
(as Rust `extern "C"`): no new keyword, no clash with the common alias
`IMPORT BNFfi AS C`.

## Types

Fixed-width C types; plain `char`, `int` and `long` are avoided because their
width is platform-defined. The header includes `<stdint.h>` and `<stdbool.h>`.

| Basic Next | C | Position |
| --- | --- | --- |
| `BOOLEAN` | `bool` | parameter, result |
| `BYTE` | `uint8_t` | parameter, result |
| `INT8`, `INT16`, `INT32`, `INT64` | `int8_t` … `int64_t` | parameter, result |
| `INTEGER` | `int32_t` (`INTEGER` is `INT32`, `0.6.md`) | parameter, result |
| `UINT16`, `UINT32`, `UINT64` | `uint16_t` … `uint64_t` | parameter, result |
| `FLOAT32` | `float` | parameter, result |
| `FLOAT64`, `FLOAT` | `double` | parameter, result |
| `STRING` | `const char *`, UTF-8, NUL-terminated, borrowed for the call | parameter only |
| `VOID` | `void` | result only |

Any other type in an `EXPORT AS "C"` signature is a language error.

**Decided 2026-10-07 (Carlos):** a C `NULL` `STRING` argument is the empty
string `""` (as if C passed `"\0"`). The BN function cannot tell `NULL` from
`""`; the header comment says so.

TODO (Carlos): a `STRING` argument that is not valid UTF-8. Recommended: the
call fails as in Runtime errors (`bn_last_error()` reports `INVALID_UTF8`, the
function body does not run, the result is the zero value). Lossy replacement
(U+FFFD) is rejected: it would change data silently.

## Diagnostics

Language (`bni check`, both backends), stable codes:

| Code | Condition |
| --- | --- |
| `C_EXPORT_NOT_FUNCTION` | `EXPORT AS "C"` on a class, struct or interface |
| `C_EXPORT_UNKNOWN_ABI` | ABI name other than `"C"` |
| `C_EXPORT_TYPE` | a parameter or result type outside the table |
| `C_EXPORT_ASYNC` | `ASYNC FUNCTION` |
| `C_EXPORT_DUPLICATE_SYMBOL` | two exported functions in the program produce the same C symbol |
| `C_EXPORT_RESERVED_SYMBOL` | the symbol collides with `main`, a `bn_` / `bn_rt_` runtime symbol, or a C keyword |

Support (W4), distinct from the above:

- `bni`: `EXPORT AS "C"` is accepted (the function stays callable from BN);
  the interpreter cannot produce a library, so `--emit sharedlib` does not
  exist there.
- `--target wasm32` with `--emit sharedlib`: support diagnostic.

## Symbol

The C symbol is the function name exactly as written (`Area` → `Area`).
Internally the function keeps its `bn_`-prefixed symbol
(`bn_llvm/src/llvm/functions.rs`); the export is a separate definition with
the C name that calls it, so BN-to-BN calls do not change.

TODO (Carlos): an explicit symbol name (`EXPORT AS "C" "geo_area" FUNCTION …`)
only if a real need appears.

## Toolchain (`bnc`)

- `--emit sharedlib`: links the module and `libbn_rt.a` into one shared
  library; the host program needs no Basic Next runtime of its own.
- A library has no `Start`: each `EXPORT AS "C"` function is an entry point
  (decided 2026-10-07, Carlos). `--emit sharedlib` on a program with a
  `Start` function is a `bnc` diagnostic, not silently ignored; a program
  with no `EXPORT AS "C"` function is a diagnostic too (an empty library).
- Header (decided 2026-10-07, Carlos): `--emit c-header`, one artifact per
  run as every other `--emit`
  (`bnc --emit c-header -o geometry.h geometry.bn`); no new option. The
  header and the library come from the same source, so they cannot drift.
  Declarations sorted by symbol (deterministic output).
- Visibility: only `EXPORT AS "C"` functions and the runtime entry points
  below are exported; everything else is hidden.
- Windows: `dllexport` on the exported symbols and an import library (`.lib`)
  for MSVC consumers. The import `.lib` is not a static library of the code.

## Runtime

### Initialisation

`Start` today performs runtime initialisation (`bn_rt_policy_init`, Windows
binary stdio). **Decided 2026-10-07 (Carlos):** every exported function is an
entry point, so the C wrapper of each one runs the initialisation once
(`std::sync::Once` in `bn_rt`) before the body. The C caller has no init
function to forget.

### Runtime errors

**Decided 2026-10-07 (Carlos):** a failed call returns the zero value of its
C result type (`0`, `0.0`, `false`; nothing for `void`) and records a
per-thread error read with `bn_last_error()`. A sentinel such as `-1` is
rejected: it is a valid result of many functions and has no `double` or
`bool` form.

```c
/* in the generated header */
typedef struct { int32_t code; const char *message; } BnError;
const BnError *bn_last_error(void); /* NULL after a successful call */
```

The error is cleared at the start of every exported call; `message` is owned
by the runtime and valid until the next exported call on the same thread.

TODO (Carlos): the mechanism, which is the largest cost of this proposal.
Today a trap branches to a block that calls `exit(1)` in the function where
it happens (`bn_llvm/src/llvm/traps.rs`), possibly many BN calls below the
exported one. To return to C:

- Recommended: in a library build a trap returns from its function with a
  per-thread failure flag set, and every BN call site checks the flag and
  returns in turn, releasing its ARC references on the way. Correct, no
  leaks; touches the emission of every call (`bn_llvm` line budget).
- Rejected: `setjmp` in the wrapper and `longjmp` from the trap. Skips the
  ARC releases of every interrupted frame (leaks) and has platform-specific
  behaviour on Windows.

### Threads

Exported functions may be called from several C threads at once. Evidence it
is reachable: ARC counts live behind one process-wide `Mutex`
(`bn_rt/src/arc_abi.rs`, `core()`); trap and error state is `thread_local!`;
module-level state is `CONST` only, so there are no mutable globals; only
scalars and borrowed strings cross the boundary, so no object is shared
between two C threads. Not a claim until a fixture calls one exported
function from several C threads and passes on the three platforms. The
global ARC lock serialises retain/release.

## Language conformance

- Spec: `0.6.ebnf` (production above), `0.6.md` (section on C export, type
  table, diagnostics), `keywords.md` unchanged (no new keyword).
- Fixtures: one negative per diagnostic code; positive: one function per type
  row, called from a C test program (`clang`) linked against the generated
  library, on Linux, macOS and Windows, with exact expected output.
- Errors: an overflow inside a nested BN call returns the zero value and sets
  `bn_last_error()`; the next successful call clears it; ARC trace shows no
  leaked object.
- Threads: one exported function called from several C threads.
- Parity: the same functions called from BN under `bni run` and `bnc` give
  the same result as the C call.
