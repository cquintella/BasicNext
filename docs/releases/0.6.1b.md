# Basic Next 0.6.1b — `BNCrypto`, the native cryptography module

**Bucket:** local `bucket-0.6.1b.md`.
**Base:** 0.6.0. Spec: `docs/language/0.6/` plus the new normative contract
[`docs/library/bncrypto.md`](../library/bncrypto.md).

## Highlights

- **`BNCrypto` is a standard-library module**, imported explicitly like every
  other `BN*` facility: `IMPORT BNCrypto AS Crypto`. It is not a `HOST`
  capability and nothing about it is built into the language.
- **Every member runs on both backends.** The primitives live in `bn_rt` behind
  the C ABI, so `bni` and `bnc` execute one implementation rather than two that
  can drift. Each family has a parity test that compiles a fixture and compares
  the native binary's output with the interpreted run byte for byte.
- **Ten algorithms:** SHA-256, SHA-512, AES-256-GCM, ChaCha20-Poly1305,
  HMAC-SHA-256, Argon2id, Ed25519, ECDSA P-256, ML-KEM-768 (FIPS 203) and
  ML-DSA-65 (FIPS 204).
- **`Crypto.Bytes` is opaque.** Key material never becomes a `STRING`
  implicitly, so it cannot be printed, concatenated or logged by accident.
  `RELEASE` frees it and a double release is reported rather than ignored.
- **Fail-closed throughout.** AEAD `Open` returns `Error` and no plaintext at
  all for a tampered ciphertext, a changed AAD or a wrong key. `FromHex` rejects
  odd-length input instead of truncating. `Slice` refuses an out-of-range window
  instead of clamping. Argon2id rejects out-of-range cost parameters rather than
  weakening them. `VerifyHmacSha256` compares in constant time.

## Verification

Conformance values come from implementations independent of the crates under
test, and are never adjusted to match output:

| Family | Checked against |
| --- | --- |
| SHA-256 / SHA-512 | Python `hashlib`, FIPS 180-4 example messages |
| AES-256-GCM / ChaCha20-Poly1305 | python-cryptography (OpenSSL) |
| HMAC-SHA-256 | Python `hmac` |
| Argon2id | **the RFC 9106 test vector**, reproduced exactly |
| Ed25519 | python-cryptography, byte for byte (RFC 8032 determinism) |
| ECDSA P-256 | interoperability: our verifier accepts an OpenSSL signature |
| ML-KEM-768 / ML-DSA-65 | **see the caveat below** |

**Post-quantum caveat.** No independent ML-KEM / ML-DSA implementation was
available to check against, so those two are *integration-verified* rather than
locally KAT-verified: round-trip agreement, key-generation determinism,
encapsulation non-determinism, tamper rejection, and object sizes equal to the
FIPS 203 / FIPS 204 parameters (1184 / 1088 / 32 and 1952 / 3309). The
algorithms themselves rest on the upstream RustCrypto crates' Wycheproof
suites. This is a weaker basis than the rest of the module and is stated
wherever the module is documented.

## Design notes

- **Deterministic encapsulation is deliberately not exposed.** `ml-kem` offers
  it, marked hidden and hazardous; reusing its randomness even once is a
  catastrophic failure, so `BNCrypto` does not offer the choice.
- **BN has no tuple**, so the pair-returning post-quantum members concatenate
  (`publicKey || privateKey`, `ciphertext || sharedSecret`) and a new
  `Crypto.Slice` splits them at sizes the standard fixes.
- **Cost:** `sha2`, `aes-gcm`, `chacha20poly1305`, `hmac`, `subtle`, `argon2`,
  `ed25519-dalek`, `p256`, `ml-kem` and `ml-dsa` are now linked into every
  compiled binary, since `bn_rt` is what `bnc` output links against.

## Not in this release

OAuth / BNWeb Auth (0.6.2), ORM field encryption (0.6.3), `HOST.Ui`, full
TLS / X.509, and RSA-RS256. `BNCrypto` supplies primitives; it takes no position
on key storage, rotation or access control, which remain the program's job.
