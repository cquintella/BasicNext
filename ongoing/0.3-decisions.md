# Basic Next 0.3 Planning Decision Record

This document is informative planning evidence. It records accepted direction,
recommendations, unresolved choices, dependency candidates, and open standards.
It cannot override `docs/language/0.3/0.3.ebnf`, `0.3.md`, or `keywords.md`.

Architecture rule: `HOST.Net` is the only built-in capability in the language
specification. Every `BNXxx` facility (`BNMath`, `BNData`, `BNLog`, `BNWeb`,
`BNJson`, and future modules) is external: a `.bn` interface backed by a Rust
provider, resolved through ordinary imports and never compiled into the core.

`BNDispatch` is the accepted 0.3 backport target for the bounded dispatch
scope previously noted as `BNThreads` in [`0.4-forward-plan.md`](0.4-forward-plan.md).
`BNCrypto` remains reserved for 0.4.

Research snapshot: 2026-08-30. Versions below are candidates, not approved
dependencies. Phase 0 must record exact versions and features before editing
`Cargo.toml`.

## Closed authority gates

### D-021 — HTTPS certificate configuration (A — accepted)

The Rustls server handshake exists, but the accepted BNWeb API does not define
where certificate and private-key material comes from. Options:

- **A — Add an explicit `TLSConfig` external BN type and `StartTLS` method.**
  Accepted. PEM inputs are bounded and held only for the lifetime of the
  provider configuration.
- **B — Keep certificate configuration host-side and register a provider before
  execution.** Pros: private keys never enter BN source. Cons: requires a host
  embedding API and makes `bn run` configuration-dependent.
- **C — Defer HTTPS server support and claim HTTPS only for the client.** Pros:
  no new API. Cons: contradicts the accepted 0.3 HTTPS server scope and blocks
  G2.

### D-022 — Stateful web API (A — accepted)

The normative 0.3 text requires isolated cookie jars, sessions, static scraping,
and ACL, but `BNWeb.bn` declares none of their public types. Options:

- **A — Add explicit `CookieJar`, `SessionStore`, `Scraper`, and `ACL` types.**
  Accepted. Operations are synchronous and bounded by the defaults below.
- **B — Add narrowly scoped methods to `Client`, `Request`, and `Server`.**
  Pros: fewer public types. Cons: couples unrelated state and policy concerns.
- **C — Keep them provider-only with no BN API.** Pros: smallest surface. Cons:
  documented 0.3 features cannot be used by BN programs, so G3/G4 cannot pass.

### D-023 — BNWeb transport callback bridge (C — accepted)

The transport provider accepts connections outside the interpreter's `Executor`,
while D-006 requires BN handlers to remain synchronous and serial. In 0.3 the
HTTP adapters therefore expose the verified Rust callback bridge only. BN route
and filter functions remain supported by explicit synchronous `Server.Dispatch`;
transport-to-BN callback projection is deferred to the 0.4 `BNWeb` revision. No unsafe
cross-thread access is permitted.

Options considered:

- **A — Bounded request queue and interpreter dispatcher.** Preserves one BN
  context but requires a new polling lifecycle and timeout contract.
- **B — Dedicated BN runtime per server.** Isolates callbacks but duplicates
  runtime state and changes `execute_with_host` lifecycle semantics.
- **C — Defer transport callbacks to the 0.4 `BNWeb` revision.** **Accepted.** Keeps the
  0.3 transport boundary safe and explicit while preserving synchronous BN
  dispatch semantics already implemented.

### D-025 — HTTP transport access logging (C — accepted)

`BNLog` resources are owned by the interpreter, while HTTP connections run in
provider threads. A transport access log must remain bounded, ordered, and
observable without crossing that ownership boundary unsafely.

- **A — Thread-safe Rust sink configured by `Server.New`.** Pros: covers
  transport access logs and keeps provider threads independent. Cons: needs an
  explicit logger-to-sink contract, flush semantics, and failure policy.
- **B — Log only explicit synchronous `Server.Dispatch`.** Pros: reuses the
  existing BN logger path with deterministic ownership. Cons: does not cover
  requests accepted by `Server.Start`/`StartTLS`.
- **C — Defer transport access logs to the 0.4 `BNWeb` revision.** **Accepted.** This
  avoids a new interop boundary; 0.3 retains bounded logging for explicit
  synchronous `Server.Dispatch` events.

### D-026 — HTTPS client trust roots (C — accepted)

The 0.3 client must validate server certificates, but the current dependency
graph has no root-certificate source. Choose an auditable provider:

- **A — `webpki-roots` static Mozilla roots.** Pros: deterministic, no host
  API, straightforward tests. Cons: roots update only when the dependency is
  upgraded and enlarge the dependency graph.
- **B — platform verifier/provider.** Pros: uses the host trust store and local
  enterprise policy. Cons: adds target-specific dependencies and makes support
  evidence/platform behavior more complex.
- **C — no HTTPS client in 0.3.** **Accepted.** The client transport and trust
  roots move to the 0.4 `BNWeb` revision; 0.3 makes no HTTPS client support claim while
  retaining the existing HTTPS server/TLS adapter.

### D-027 — Available processor count (accepted)

`BNDispatch` needs a portable, bounded worker-pool default without confusing
physical cores with logical processors or ignoring process-level CPU limits.

The accepted spelling is `HOST.NumProcs() AS INTEGER OR Error`. It returns the
number of logical processors available to the current process, including host
or container affinity limits where the operating system reports them. The Rust
provider uses `std::thread::available_parallelism()`; it returns `Error` when
the host cannot report a usable value. `BNDispatch.Queue.Auto()` may use this
method. The name deliberately follows OpenMP's `omp_get_num_procs` convention
and does not make a physical-core claim.

This is an accepted Sprint 12 API decision, not implemented 0.3 behavior yet.
The Sprint 12 gate must update the normative HOST documentation, semantic/IR/
runtime support, fixtures, and capability evidence together before the method
is claimed as available.

### D-028 — Dispatch ticket lifecycle (accepted)

`BNDispatch` needs an explicit, bounded representation of scheduled work that
does not expose operating-system thread handles or require a generic result
type.

`Queue.Async(work AS FUNCTION() AS VOID OR Error) AS Ticket OR Error` returns
an opaque `Ticket`. Its public interface is:

```basic
Id() AS INTEGER
Status() AS INTEGER
Wait(timeoutMs AS INTEGER) AS VOID OR Error
Cancel() AS BOOLEAN OR Error
Error() AS Error OR NA
IsDone() AS BOOLEAN
Close() AS VOID
```

`BNDispatch` exports integer constants `PENDING`, `RUNNING`, `COMPLETED`,
`FAILED`, and `CANCELLED`. `Cancel()` succeeds only while the ticket is
`PENDING`; running work is never terminated forcefully. `Wait()` preserves a
task failure, cancellation, queue closure, or timeout as `Error`.
`Error()` returns the retained task error only for `FAILED`, otherwise `NA`.
`Close()` releases ticket metadata and invalidates later operations. Queue
closure cancels pending work, waits only up to its supplied deadline for
running work, and never leaves a waiter blocked indefinitely. Typed task
results are deliberately deferred; the initial task signature is
`FUNCTION() AS VOID OR Error`.

### D-029 — Dispatch task output (accepted)

Task output is visible on the submitting interpreter's output stream. Output
from distinct workers has no ordering guarantee. Workers send output bytes to
the queue through synchronized message passing; only the submitting executor
writes its owned output stream. This avoids sharing `&mut Write` across
threads and keeps the runtime free of `unsafe` code.

## Minimum API decisions

Phase 0 must resolve these items in the normative host/module contracts. No
implementation activity may invent an answer locally.

### `HOST.Net`

- value types for IP addresses, CIDRs, endpoints, TCP streams/listeners, and
  UDP sockets;
- opaque collection types with `Count` and `Get` for variable-size resolver
  results; variable-size BN vectors are not available in 0.3;
- parse/format equality and IPv4/IPv6 normalization rules;
- forward and reverse system-resolution behavior, ordering, timeouts, and
  empty-result behavior;
- connect, bind, listen, accept, send, receive, EOF, timeout, and idempotent
  close behavior;
- one-shot `Ping(address, timeout)` for IPv4 and IPv6, returning the responding
  address and round-trip microseconds; name resolution remains a separate
  operation;
- typed timeout, unreachable, permission-denied, and operation-unavailable
  results for ICMP Echo;
- all-or-nothing dual-stack listener startup;
- direct-neighbor lookup availability and error behavior, with no raw packet
  access or neighbor-table mutation;
- ownership after return, close, handler failure, and interpreter shutdown.

### `BNWeb`

- opaque collection types for headers, query values, cookies, route
  parameters, and selector results;
- URL parsing and normalization boundary;
- request body consumption, response commit, duplicate-header, and error
  behavior;
- ordered literal and `:name` route matching, automatic `404`, and automatic
  `405` with `Allow`;
- server lifecycle. The smallest recommended surface is explicit start,
  bounded dispatch of one request, stop, and idempotent close; it avoids async
  BN syntax and hidden concurrent execution;
- HTTP client redirect, DNS rebinding, private-address, timeout, TLS, cookie,
  and decompression policy;
- trusted-proxy provenance and the distinction between peer address,
  effective client address, HTTP `Origin`, and local destination;
- session identifier generation, rotation, expiry, capacity, and eviction;
- static scraping only: no script, event handler, subresource, or browser
  execution;
- ACL ordering/default action, logging failure behavior, and optional
  geolocation-provider failure behavior.

### ICMP provider plan

| Host | Preferred 0.3 provider | Required evidence |
|---|---|---|
| Linux | Unprivileged ICMP datagram socket; no raw-socket fallback required for a support claim | IPv4/IPv6 loopback as a non-root user, permitted and denied `ping_group_range`, timeout, and unavailable results |
| Windows | Native IP Helper ICMP APIs for IPv4 and IPv6 | IPv4/IPv6 loopback without Administrator privileges, timeout, and unavailable-stack results |
| macOS | Decision pending a native-provider spike | If unprivileged IPv4/IPv6 evidence is absent, report Ping unavailable without disabling other Net operations |
| Other hosts | No assumed provider | Deterministic operation-unavailable result |

The implementation must never parse localized output from or execute an
external `ping` program. Raw-socket privilege is not a prerequisite for
claiming baseline TCP/UDP/resolver support.

### `BNLog`

- fixed typed `ERROR`, `WARN`, `INFO`, `HTTP`, `VERBOSE`, `DEBUG`, and `SILLY`
  levels with per-logger and per-transport filtering;
- opaque bounded structured fields and immutable child-logger context;
- JSON Lines, escaped text, and Apache Combined formats;
- console, append-only file, and null transports only in 0.3;
- synchronous ordered dispatch that attempts all eligible transports and
  returns the first error;
- explicit flush and idempotent close;
- default redaction/exclusion rules for authorization, cookies, sessions,
  bodies, query values, and TLS private material;
- no HTTP transport, background queue, formatter callback, custom level,
  rotation engine, or Node.js dependency in 0.3.

must fail with a typed error rather than allocate without a bound.

## Risk register

| Risk | Impact | Control |
|---|---|---|
| Public API invented during implementation | High: incompatible module surface | G0 freezes types, signatures, ownership, errors, and limits first. |
| Synchronous BN handlers over asynchronous transports | High: deadlock or hidden concurrency | D-006 and G0 freeze one bounded serial-dispatch model. |
| SSRF through redirects, DNS changes, or IPv4/IPv6 differences | High: trust-boundary bypass | G0 policy plus G2 local rebinding, redirect, and private-CIDR tests. |
| Pre-1.0 HTTP/3 stack | High: release and interoperability instability | D-007 removes it from the 0.3 graph and release gate. |
| GeoLite licensing mistaken for open-source data | High: redistribution exposure | External provider only; G3 checks artifacts and download behavior. |
| ARP/NDP and transparent IPsec vary by operating system | Medium: false portability claims | Capability matrix and per-host evidence; deterministic unavailable result. |
| ICMP Echo requires different APIs or privileges by host | Medium: `Ping` works only on privileged development machines | D-016 requires unprivileged-host evidence and per-operation unavailable/permission results. |
| Alpha DAP framework or excess protocol surface | Medium: maintenance instability | Shared JSON framing and only the accepted DAP message subset. |
| Unbounded protocol or parser resources | High: denial of service | Activity 0.3 freezes byte, count, queue, time, and retained-state bounds. |
| Logging recursively invokes `BNWeb` | High: recursion and outage amplification | D-013 forbids a BNLog HTTP transport in the 0.3 core. |

## Release gates

1. **G0 — API and threat model:** resolve D-005, D-006, D-014, D-019, and the
   operational limits.
2. **G1 — dependency approval:** resolve D-004, D-009, D-010, D-016, and
   approve the exact locked graph before adding production crates.
3. **G2 — HTTP baseline:** local HTTP/1.1, HTTP/2, TLS, limit, timeout, and SSRF
   evidence must pass.
4. **G3 — optional data:** resolve D-008; geolocation ships only as an optional
   provider with operator-supplied data and deterministic unavailable behavior.
5. **G4 — release:** every support claim has local executable evidence; no
   test requires a public Internet service.
