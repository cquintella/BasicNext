# Basic Next 0.4 Forward Plan

This is a forward-looking scope note. It does not change the accepted 0.3
contract and does not authorize implementation in the 0.3 release.

## External modules

- `BNThreads`: mandatory external module backed by Rust providers for bounded
  threads, semaphores, and mutexes. The 0.4 release cannot close without a
  semaphore API and conformance evidence; semaphores are required for bounded
  admission/coordination in addition to thread creation and mutex ownership.
- `BNCrypto`: external module backed by Rust cryptographic providers.
- Optional geolocation provider: revisit an operator-supplied MMDB interface;
  no geolocation dataset is bundled or downloaded by Basic Next.
- `BNWeb` revision: the 0.4 WebServer may opt into threaded request handling
  through `BNThreads`; the 0.3 serial-handler contract remains unchanged. The
  revision also owns HTTP transport access-log delivery to `BNLog` through a
  bounded, ordered thread-safe sink, and the deferred HTTPS client transport
  with an approved platform/static trust-root provider.

Both modules require explicit `IMPORT` and remain outside the language core.
Neither module is part of the 0.3 dependency graph or release gate.
The `BNWeb` revision is also a 0.4 change and must not be backported into the
0.3 lifecycle contract.

## Experimental operating-system target

- Add **Haiku OS** as an experimental 0.4 target, beginning with
  `x86_64-unknown-haiku` and adding `i686-unknown-haiku` only if a maintained
  toolchain and CI runner are available.
- Reuse the frontend, interpreter, and standard-library-first `HOST.Net`
  implementation where the Rust target provides it; isolate Haiku-specific
  providers behind target-specific modules.
- Do not claim Haiku support until a native Haiku build, interpreter smoke
  suite, TCP/UDP/resolver tests, and capability matrix run succeed on Haiku.
- Tokio-dependent HTTP services are not assumed to work on Haiku. The 0.4
  port must either provide a supported runtime adapter or report the affected
  capabilities as unavailable without weakening core language support.
- Haiku ICMP, TTY, filesystem, TLS, and thread behavior require independent
  host evidence; unsupported capabilities remain deterministic `Error` results.

## Decision gates before implementation

- Define ownership, lifetime, shutdown, and failure behavior for thread and
  synchronization handles.
- Define the semaphore contract before implementation: permit count bounds,
  acquire/release behavior, timeout/cancellation, fairness, shutdown, and
  behavior when a permit is unavailable.
- Decide whether BN code may execute concurrently or whether concurrency is
  restricted to host/provider tasks.
- Define deadlock, poisoning, cancellation, and resource-limit behavior.
- Define the threaded `BNWeb` server model: opt-in versus default, worker
  ownership, request isolation, ordering guarantees, graceful stop, and
  interaction with `BNLog` and `HOST.Net`.
- Select audited cryptographic primitives and providers; freeze key ownership,
  secret memory handling, randomness, algorithm agility, and unavailable-host
  behavior.
- Add normative grammar/module entries and conformance fixtures together with
  each accepted API.
