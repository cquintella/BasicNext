# Basic Next 0.4 Active Security Register

This is the active security register for the 0.4 program. The 0.3 audit
documents under `done/project/` and `done/0.3-*.md` are historical evidence;
they are not a substitute for this register. Findings are based on the 0.3
Rust implementation, the 0.3 BNWeb contract, and the 0.4 production-hardening
review.

## Register policy

Every finding remains open until its code change, focused regression test,
documentation update, and residual-risk decision are recorded. Security tests
must use local resolver/socket/TLS fixtures and bounded deterministic clocks;
they must not depend on public Internet services. No finding authorizes a
change to the accepted 0.3 contract without a corresponding normative update.

## Findings

### BN-SEC-001 — IPv4-mapped IPv6 SSRF classification

- **Severity:** Critical.
- **Status:** Mitigation in progress — classifier and focused regression tests landed; literal/post-DNS/redirect parity and documentation remain open.
- **Affected code:** `src/web.rs::validate_ssrf_destinations`; client URL and post-resolution paths in `src/http.rs` and `src/runtime/executor/part4.rs`.
- **Root cause:** The IPv6 branch checks IPv6-only predicates but does not reclassify `::ffff:a.b.c.d` as IPv4 before applying private, loopback, link-local, or metadata-range policy.
- **Scenario:** With private destinations disallowed, `::ffff:127.0.0.1`, `::ffff:10.0.0.1`, or `::ffff:169.254.169.254` can be treated as a public IPv6 destination and reach a local service or metadata endpoint.
- **Mitigation:** Use one destination-classification helper. If an IPv6 address is IPv4-mapped, apply the complete IPv4 policy; otherwise apply the IPv6 policy. Call it after literal parsing, every DNS result, and every redirect.
- **Required tests:** Reject mapped loopback, RFC1918, link-local/metadata, multicast, unspecified, and CGNAT values; allow a documented global IPv6 and public IPv4 value; cover literal URL, resolver result, mixed result, and redirect paths.
- **Documentation impact:** State in `docs/language/0.3/bnweb.md` and the 0.4 BNWeb contract that IPv4-mapped IPv6 is classified as the corresponding IPv4 address.
- **Residual risk:** DNS rebinding and platform resolver behavior remain risks unless every redirect/hop is re-resolved and checked; the allowlist `EgressPolicy` is stronger than the default denylist.
- **Owner/activity:** WBS-0.4 Activities 1.1 and 1.2.
- **Current evidence:** `src/web.rs` now reclassifies IPv4-mapped IPv6 through the IPv4 helper; `web::tests::ssrf_guard_reclassifies_ipv4_mapped_ipv6_as_ipv4` passes. The finding remains open until every resolution/redirect path is covered.

### BN-SEC-002 — Incomplete special IPv4-range policy

- **Severity:** High.
- **Status:** Mitigation in progress — special-range classifier and focused regression tests landed; central policy documentation and all egress paths remain open.
- **Affected code:** `src/web.rs::validate_ssrf_destinations`.
- **Root cause:** `Ipv4Addr::is_private()` covers RFC1918 but not CGNAT `100.64.0.0/10`, documentation ranges, or benchmark `198.18.0.0/15`.
- **Scenario:** A client policy intended to reject non-public destinations can connect to carrier-grade NAT or reserved/test ranges, defeating operator assumptions and potentially reaching provider or internal routing surfaces.
- **Mitigation:** Centralize `is_non_routable_or_sensitive_v4` for RFC1918, loopback, link-local, unspecified, multicast, CGNAT, documentation, benchmark, and explicit metadata ranges. Keep ULA/link-local/loopback checks for non-mapped IPv6.
- **Required tests:** Reject `100.64.0.1`, `100.127.255.254`, `198.18.0.1`, all documentation blocks, and mapped equivalents; allow a documented global address; test allow-private opt-in.
- **Documentation impact:** Publish the exact range list and explain that an explicit CIDR allowlist is preferred for production egress.
- **Residual risk:** Range classification cannot prove public reachability; production deployments should use `EgressPolicy` and network-level controls.
- **Owner/activity:** WBS-0.4 Activities 1.1 and 1.3.
- **Current evidence:** `src/web.rs` now rejects CGNAT, documentation, benchmark, and mapped equivalents; `web::tests::ssrf_guard_rejects_special_ipv4_ranges_but_allows_global_ipv4` passes.

### BN-SEC-003 — Predictable session identifiers

- **Severity:** High.
- **Status:** Mitigation in progress — CSPRNG IDs and focused tests landed; injectable entropy failure and cookie-policy integration remain open.
- **Affected code:** `src/web_state.rs::SessionStore::create` and `rotate`.
- **Root cause:** IDs are generated as `s{:016x}` from an incrementing `u64` counter.
- **Scenario:** An attacker who obtains one session ID can enumerate adjacent IDs and attempt session takeover while the session remains alive.
- **Mitigation:** Generate at least 16 bytes using the approved CSPRNG (`ring::rand::SystemRandom` or the provider frozen by the 0.4 decision gate), encode as bounded hex/base64url, and never derive IDs from counters, time, or process identity. Remove the old ID before rotation creates a new one.
- **Required tests:** Minimum encoded length, uniqueness over a controlled sample, non-adjacency, rotation invalidation, capacity/expiry behavior, and provider failure without insertion.
- **Documentation impact:** Update session and cookie contract with entropy, rotation, expiry, and logging requirements.
- **Residual risk:** In-memory sessions remain process-local and are lost on restart; persistent/distributed sessions remain outside the base 0.4 scope.
- **Owner/activity:** WBS-0.4 Activities 2.1 and 2.2.
- **Current evidence:** `SessionStore::create` now uses 16 bytes from `ring::rand::SystemRandom`; `web_state::tests::session_ids_are_random_and_have_at_least_128_bits` and `entropy_failure_does_not_insert_a_session` pass. The finding remains open until the provider is wired through the complete session/cookie API and documentation is complete.

### BN-SEC-004 — Unbounded per-connection thread creation

- **Severity:** High.
- **Status:** Open.
- **Affected code:** `src/runtime/executor/part4.rs` `Start` and `StartTLS` accept loops.
- **Root cause:** Each accepted connection calls `std::thread::Builder::spawn` without a global admission semaphore/counter. The existing pending-request bound does not limit accepted sockets or connection threads.
- **Scenario:** A client opens many connections or holds them slowly, exhausting threads, memory, or file descriptors before the internal request queue reaches its limit.
- **Mitigation:** Apply a shared finite `max_connections` admission control before spawning; define backlog and overload behavior; move connection handling to an approved shared Tokio runtime or fixed worker pool; enforce the same policy for cleartext and TLS.
- **Required tests:** Controlled `N+1` connections, slow peers, TLS and cleartext parity, active worker cap, rejection status/close behavior, worker failure isolation, and recovery after disconnect.
- **Documentation impact:** Add quotas, defaults, `429` versus `503` semantics, and provider limitations to the BNWeb contract.
- **Residual risk:** Kernel backlog and descriptor limits remain host-level controls and must be recorded in deployment evidence.
- **Owner/activity:** WBS-0.4 Activities 3.1 and 3.2.
- **Current evidence:** `ServerState` now accounts admitted connections against the registered active-connection limit before either cleartext or TLS worker spawn, and releases the slot on worker completion or spawn failure. `web::tests::server_admission_bounds_connections_before_worker_spawn` passes. Backlog policy, explicit overload response, fixed worker pool, and lifecycle join remain open.

### BN-SEC-005 — Incomplete graceful stop and connection tracking

- **Severity:** High.
- **Status:** Open.
- **Affected code:** `src/runtime/executor/part4.rs` listener/connection lifecycle; `src/web_state.rs` stop/close state.
- **Root cause:** Listener and connection threads are not retained as joinable server-owned handles. `Stop` changes state but does not reliably stop, drain, and join all admitted work before returning.
- **Scenario:** A server reports stopped while workers or sockets remain live, causing resource leakage, late responses, process shutdown races, or inconsistent restart behavior.
- **Mitigation:** Track listener and connection tasks, stop accepting before drain, signal active work, cancel pending work by policy, join with a deadline, and return a typed timeout/error when work cannot drain.
- **Required tests:** Idle/active/slow/failing connections, repeated stop, close-after-stop, stop deadline expiry, no new accepts after drain begins, and zero untracked workers after successful close.
- **Documentation impact:** Define lifecycle states and exact stop/close ownership and deadline semantics.
- **Residual risk:** A forceful process termination can still interrupt external OS operations; the API must report deadline expiry rather than claim successful drain.
- **Owner/activity:** WBS-0.4 Activities 2.5 and 3.3.

### BN-SEC-006 — Missing default response security and cookie policy

- **Severity:** Medium.
- **Status:** Open.
- **Affected code:** `src/http.rs` response construction; `src/web.rs` response/cookie state; BNWeb documentation.
- **Root cause:** Body/header bounds exist, but safe default response headers and typed `Secure`/`HttpOnly`/`SameSite` cookie policy are not a complete immutable server configuration.
- **Scenario:** Applications omit security headers or emit session cookies without protections, increasing exposure to content-type confusion, transport downgrade mistakes, and client-side session theft.
- **Mitigation:** Add immutable `Server.Options`, strict header profile with `X-Content-Type-Options: nosniff` and HTTPS-only HSTS, and typed cookie attributes with explicit HTTPS/proxy semantics. Reject conflicting duplicate defaults.
- **Required tests:** HTTP/1.1 and HTTP/2, cleartext/TLS, strict profile, invalid combinations, cookie serialization/parsing, and no HSTS over cleartext.
- **Documentation impact:** Update BNWeb and usage docs with defaults, proxy termination rules, and explicit opt-in headers such as CSP/frame policy.
- **Residual risk:** Headers cannot replace application authorization or browser-specific policy review.
- **Owner/activity:** WBS-0.4 Activities 2.2, 2.3, and 2.4.
- **Current evidence:** HTTP responses now receive `X-Content-Type-Options: nosniff`; TLS responses additionally receive HSTS, while cleartext responses do not. `http::tests::default_security_headers_are_transport_aware` passes. Typed cookie policy and immutable public `Server.Options` remain open.

### BN-SEC-007 — Log redaction and observability leakage

- **Severity:** Medium.
- **Status:** Open.
- **Affected code:** `src/log.rs`, HTTP access-record mapping, explicit BNLog fields.
- **Root cause:** Existing denylist covers several sensitive names, but production hardening requires broader case-insensitive handling, mandatory redaction boundaries, and consistent control-character escaping across formats.
- **Scenario:** A credential, session token, query value, proxy secret, or log-injection control sequence reaches an explicit field or a format-specific renderer.
- **Mitigation:** Expand the denylist/typed redaction policy for credentials, authorization variants, cookies, session IDs, API keys, passwords, tokens, private keys, proxy data, query/body fields, and common secret names; enforce bounded escaping in JSON Lines, text, and Apache formats. Add request IDs and bounded stats without content or external telemetry.
- **Required tests:** Secret-name/value matrix, case variants, control characters, all formats/transports, explicit-field bypass attempts, request correlation, counter saturation, and committed-response logging failure.
- **Documentation impact:** State mandatory exclusions and request-ID/statistics contents in BNLog and BNWeb contracts.
- **Residual risk:** Operators can still log secrets intentionally outside BNLog; application guidance and deployment log access controls remain necessary.
- **Owner/activity:** WBS-0.4 Activities 4.1 and 4.2.

## Release rule

No 0.4 production-hardening or concurrent-BNWeb claim is accepted while a
critical/high finding is open without an explicit risk acceptance. A finding
may be closed only with source evidence, focused regression tests, updated
normative documentation, and the repository quality gate:

```text
cargo fmt --check
cargo test
cargo clippy --all-targets -- -D warnings
git diff --check
```
