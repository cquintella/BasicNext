# Basic Next 0.6.0 — two executables (`bni`, `bnc`) and `++`/`--` expressions

**Buckets:** local `bucket-0.6.0.md` (toolchain split, SPRINTs 1–3) and
`bucket-0.6.1.md` (language S1', shipped in this same tag).
**Base:** 0.5.2.1 (`52764c4`). Spec: `docs/language/0.6/` (opened as a copy
of 0.5, amended by S1').

## Highlights

- **Two executables replace `bn`.** `bni` is the interpreter and the
  frontend tool (`run`, `eval`, `check`, `lex`, `lsp`, `dap`); `bnc` is the
  compiler with a Clang-like surface: `bnc [compile-options] <entry.bn>`
  (`-o`, `--target native|wasm32`, `--opt`, `--emit`). Both are thin
  compositions over shared libraries: `bn_cli` (options, `config.toml`,
  frontend adapter, `check`, diagnostics, output, process log),
  `bn_frontend::prepare` (one load → analyze → lower → validate call used by
  CLI, LSP and DAP), `bn_interpret_driver` (run/eval, HOST environment,
  provider registries, `lib-*` features), `bn_compile_driver` (build,
  toolchain discovery, artifact linking), `bn_lsp`, `bn_dap`.
- **Dependency gates.** `bnc` links no interpreter, `tokio`, `hyper` or
  `rustls`; `bni` links no LLVM backend; `bni --no-default-features` is the
  language + HOST build.
- **One workspace version.** `[workspace.package] version = "0.6.0"`;
  `bni --version` and `bnc --version` agree.
- **Release assets:** `bni-<os>-<arch>`, `bnc-<os>-<arch>`,
  `libbn_rt-<os>-<arch>.a`, `bni.1`, `bnc.1`, `SHA256SUMS`. Installers
  (`scripts/install.sh`, `install.ps1`) install and verify both binaries and
  still recognise pinned 0.5 tags (`bn` + `bnc`).
- **IDE:** the VS Code extension and the Jupyter kernel launch `bni`
  (falling back to `bn` only on a 0.5 installation).

## Breaking changes

- The `bn` executable is removed (Carlos, 2026-09-22; the interim
  dispatcher never shipped). `bn run|eval|check|lex|lsp|dap …` → `bni …`;
  `bn build [opts] file` → `bnc [opts] file`. The 0.5 `bnc` wrapper profiles
  (`-c`, `--check`, default-interpret) are gone.
- `--target`/`--opt` are compiler options only: `bni` rejects them
  (`bn run` used to accept and ignore them).
- Python tooling: `tests/test_*.py` read `BN_INTERPRETER` / `BN_COMPILER`
  (defaults `target/debug/bni|bnc`).

### Language: `++` / `--` as expressions (S1', bucket 0.6.1)

- **Prefix and postfix increment/decrement expressions, C convention.**
  `++t` / `--t` update `t` and yield the **new** value; `t++` / `t--`
  update `t` and yield the **old** value. With `t = 100`: `PRINT ++t` → `101`,
  `PRINT t++` → `100`. The statement forms of 0.5.2 (`t++` alone on a line)
  are unchanged.
- **Operand rules.** The operand is an assignment target (binding, member,
  element) with the typing of `t += 1`; literals, call results and casts are
  syntax errors; the forms do not chain. Overflow is checked exactly as
  `+= 1` (`NUMERIC_OVERFLOW`, both backends) and raised before any value is
  yielded.
- **No IR change.** Lowering reuses the compound-assignment sequence and the
  shared store-to-target path; interpreter and LLVM produce identical output
  (`tests/test_compiler_parity.py` gains both increment fixtures).

**Breaking:**

- `PRINT i++` and `x = i++`, syntax errors in 0.5.2, are now valid programs
  (postfix, old value). Code that relied on the rejection has none to keep.
