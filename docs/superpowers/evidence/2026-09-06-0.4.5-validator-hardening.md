# Bucket 0.4.5 — IR validator hardening

Date: 2026-09-06

## Implemented

- Rejected duplicate `ValueId` definitions across a function, preserving the
  single-assignment invariant required by the explicit `Phi` design.
- Rejected `Phi` instructions after any ordinary instruction in a block; merge
  values must be available at block entry.
- Rejected non-BOOLEAN branch conditions and incompatible `Stop`/`Return`
  values at the function boundary.
- Checked `Phi` incoming types, copy types, and dynamic `LEN`/`SIZEOF` result
  types using literal, alternative, and dynamic-pointer compatibility rules.
- Checked constant categories against their declared IR types, including
  literal, host, module, function, null and sentinel forms; added a negative
  fixture for a boolean constant declared as an integer.
- Checked fixed vector literals against their declared first dimension and
  added a negative shape fixture; dynamic dimensions remain represented by
  the existing `u64::MAX` marker.
- Kept existing all-path CFG, predecessor, operand-use and target-separation
  checks unchanged.
- Added negative fixtures for the structural and type invariants in
  `tests/validated_ir.rs`.
- The detailed type-boundary rules and their intentional `Named`-type
  limitation are recorded in [validator type evidence](2026-09-06-0.4.5-validator-types.md).
- The new uniqueness check exposed an existing lowering defect in short-circuit
  expressions; that producer now emits explicit branch values and a join `Phi`.
  The targeted CLI regressions are recorded separately.
- `load_frontend` now lowers and validates once into a `ValidatedModule` before
  returning to the CLI controller. `check`, `run`, and `build` consume that
  same artifact; this removes the previous successful `check` path that could
  stop after semantic analysis and provides direct W1–W3 evidence.
- Added language-level contracts for `Unary`, `Binary`, `Cast` and typed
  `Call` instructions. Invalid operator categories, conversions and
  non-function callees now fail during IR validation; known function
  signatures also have their argument and result types checked.
- The `IS` binary form additionally requires the lowered right operand to be
  a type-test constant, while preserving the existing boolean result rule.
- HOST console controls now reject any operand other than `HOST.Console` at
  the language IR boundary.
- Store-like instructions now verify the assigned operand against their
  declared `ty`: `Store`, `SetIndex`, `SetMember`, `SetField` and
  `StoreStatic`; dedicated negative fixtures cover the scalar store and the
  member/field/static variants.
- `Index` now validates the indexed object and result relationship: vectors
  consume one dimension at a time, pointers return their element type, and
  strings/`HOST.Args` return `STRING`; non-indexable objects and mismatched
  results have dedicated negative fixtures.
- Structural identity checks reject empty member names, static class/field
  names and class-initialization names; member metadata resolution remains a
  separate architectural contract because the current IR carries no class
  member table.
- Dispatch IR now validates the provider-independent operand contract:
  `Queue`, synchronization handles (`Ticket`, `Group`, `Barrier`, `Semaphore`,
  `Mutex`), integer wait timeout and function task. Provider callees remain
  `Unknown` by design and are checked by target support/runtime layers. This
  exposes a specification gap: the current 0.4 text documents `AWAIT` only for
  `Ticket`, while existing provider methods lower through the same IR opcode.
- Assignment validation preserves runtime pointer-length checking: compatible
  pointer elements may be stored across fixed/dynamic length declarations, so
  a computed length mismatch remains the defined `POINTER_LENGTH_MISMATCH`
  runtime error rather than being misclassified as invalid IR.
- LLVM support diagnostics now preserve the support category at the
  `validate_for` boundary: unsupported type-shaped operations use
  `TARGET_UNSUPPORTED_TYPE`, generic unavailable operations use
  `TARGET_UNSUPPORTED_OP`, HOST capability failures use
  `TARGET_UNSUPPORTED_HOST`, and entrypoint failures retain their dedicated
  code. The diagnostic catalog contains the new stable support IDs, and the
  configured `bn build` integration path asserts that the type-support code
  reaches CLI stderr.
- Aligned call validation with the language's existing numeric-literal
  coercions and dynamic vector dimensions, preserving valid BNMath, network
  and other intrinsic calls; numeric compatibility also applies recursively
  to vector elements (as exercised by `BNMath.MEAN` in `language-tour`).
- LLVM support analysis now checks integer and floating literal parsing before
  emission. A language-valid IR fixture with an unparsable integer is rejected
  by `validate_for` as `TARGET_UNSUPPORTED_OP`.
- `DispatchSubmit` now rejects non-empty task argument lists in support
  analysis, matching the compiled task ABI's existing emission constraint;
  this prevents that mid-emit failure from being the first diagnostic.
- Vector `Default` support now requires an element LLVM type that the emitter
  can actually zero-initialize; non-scalar elements are rejected as
  `TARGET_UNSUPPORTED_TYPE` before emission.
- Fixed vector lowering now also rejects dimensions outside the `u32` range
  used by the LLVM emitter, preventing an oversized dimension from being
  silently converted to zero.
