# Basic Next 0.4 Concurrency and Provider Decision

This document records the implementation contract for the bounded
`ASYNC`/`AWAIT` feature and opt-in concurrent BNWeb. It is subordinate to the
accepted 0.4 language and threat-model documents until Carlos accepts it.

All connection, queue, worker, timeout, identity, and rate-limit thresholds
come from the versioned registry
[`config/0.4-bnweb-limits.toml`](../config/0.4-bnweb-limits.toml). The
concurrency implementation must consume a typed snapshot of that registry;
there is no per-module fallback constant.

## Proposed contract

### Provider and worker model

- `BNDispatch` is an explicit external module; `HOST` remains the only built-in
  interface object.
- The native Rust host provides a fixed worker pool per `Dispatch.Queue`.
- A queue has a finite worker count and pending-ticket capacity. Submission
  fails deterministically when either limit is reached; it never creates an
  unbounded thread or a runtime per ticket.
- The initial provider is native-interpreter only. Compiler, Jupyter, and wasm
  hosts report `HOST_CAPABILITY_UNAVAILABLE` until they provide the same
  contract.
- No new dependency or `unsafe` code is introduced for this feature.

### Task ownership and arguments

- An async target is a named function and executes in an isolated module/runtime
  copy.
- Arguments are evaluated once, left to right, before submission.
- Arguments must be immutable, scalar, or explicitly clonable BN values. The
  semantic analyzer rejects mutable aliases, caller frames, raw descriptors,
  thread handles, and output writers.
- The worker owns its local frame and values for the task lifetime. Completion
  retains only the bounded result/error and ticket state.

### Ticket, await, and cancellation

- Submission returns one opaque `Dispatch.Ticket OR Error`.
- `AWAIT` accepts 1–60,000 milliseconds and may be repeated after completion.
- A timeout stops waiting; it does not force-kill a running task. The ticket
  remains owned by the caller and may be awaited again.
- Queue close cancels pending tickets. Running tasks finish cooperatively and
  are not forcefully killed by the initial provider.
- A task failure is retained as a typed `Error`; it is never silently converted
  to success.

### Output and response ownership

- Async task output is forwarded through a synchronized, bounded ticket
  channel. The normative limit is the versioned
  `dispatch.output_max_bytes` registry value. Workers enforce it at the writer
  boundary before converting bytes to a `String`; overflow is an explicit
  task/output error and never permits unbounded retained output or a successful
  ticket.
- Concurrent BNWeb is opt-in and uses one request task per admitted request.
- Exactly one request owner may commit a response. A timeout, cancellation, or
  handler failure closes the response if it has not been committed.
- The transport does not reuse a connection until the response owner has
  completed or the connection has entered an explicit failure/close state.
- A blocking handler task is not considered drained when its connection future
  times out. The implementation must retain ownership until completion or use a
  cooperative cancellation protocol; dropping a `spawn_blocking` join handle
  is insufficient evidence for `Stop`/`Close`. The server therefore retains an
  atomic active-handler count and returns a drain timeout while it is nonzero.
- Synchronous 0.3 dispatch remains the default and keeps its serial response
  and output ordering.

### Shutdown and observability

- `Stop` first transitions the server to `Draining`, then stops admission,
  closes pending queue work, waits for admitted tasks, and joins workers before
  its deadline.
- A deadline returns an explicit stop-timeout result and never reports a false
  successful drain.
- Queue, ticket, request, and response transitions are observable through
  bounded, redacted BNLog records; secrets and request bodies are excluded.

## Required decision tests

Before implementation, the contract must have local tests for worker-pool
bounds, pending-ticket rejection, argument isolation, repeated await,
timeout-with-running-task, pending cancellation on close, retained task
failure, bounded output, exactly-once response commit, stop/drain deadline,
and preservation of synchronous 0.3 behavior. The output test must exercise
both the direct ticket boundary and the worker writer, and must assert that
overflow yields a failed ticket with an explicit diagnostic.

## Acceptance

Status: **ACCEPTED — 2026-09-01.** Carlos approved this contract. It is the
normative gate for Activities 3.2, 3.3, 5.1, and 5.2. Any change to provider,
ownership, cancellation, response, output, or shutdown semantics requires a
new decision record and regression review.

The BN handler bridge remains a separate open implementation gate: the live
interpreter `Executor` owns mutable heaps and output references and must not be
captured by a connection thread. Activity 5.2 must either factor a fresh,
isolated executor/marshalling boundary or obtain an explicit scope decision to
defer BN callback execution; transport-level Rust handler tests alone do not
close that gate.
